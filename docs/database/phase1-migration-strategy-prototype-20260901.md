# Phase 1 migration-layout prototype

Checkpoint: 2026-09-01. Production remained read-only.

## Verified CLI behavior

Supabase CLI was absent from `PATH`. Version `2.116.0` was downloaded into a
temporary workspace-only pnpm cache and executed without installing a runtime
dependency. The required help commands were inspected.

- `migration squash` accepts `--version`, `--db-url`, `--linked`, `--local`,
  password and project-ref options. It changes migration representation and is
  not an appropriate production validation mechanism.
- `migration repair <version...> --status applied|reverted` changes the target
  migration history. It requires separate production approval.
- `db push --dry-run` prints migrations it would apply. `--include-all` includes
  versions absent from remote history; `--include-seed` and `--include-roles`
  broaden the operation; vault is touched unless `--skip-vault` is supplied.
- `migration list` compares local and remote history but requires a local stack,
  DB URL, or linked project credentials.

## Required separation

### Fresh-install baseline

Keep the candidate outside the current active `supabase/migrations` directory
until layout approval. It must be generated by `supabase migration new`, begin
with an unconditional sentinel assertion, and abort if any of these exist:
`public.profiles`, `public.lego_sets`, `public.collection_items`,
`public.growth_events`, or `public.exchanges`. There is no production/assertion
branch inside the migration.

Creation order:

1. required extensions;
2. BrickCircle-owned types and sequences;
3. all 21 BrickCircle-owned tables, columns, defaults and constraints;
4. all indexes and any views;
5. RLS enablement and exact checkpoint policies;
6. exact functions with security mode and search path;
7. supported triggers on BrickCircle tables and `auth.users`;
8. explicit table, sequence and function revokes/grants, including Data API
   access for `anon`, `authenticated` and `service_role`;
9. supported storage policies on managed `storage.objects`.

It must not create Supabase-managed schemas or tables. Bucket rows, cron rows and
reference/catalogue data are excluded from the DDL baseline.

### Production validation

`supabase/validation/production_catalog_fingerprint.sql` is a separate
SELECT-only script. It normalizes columns, constraints, indexes, policies,
functions, triggers and ACLs, then fingerprints storage and cron separately.
Expected hashes are approval-controlled evidence, not embedded DDL.

### Production history alignment

History alignment is a separately approved operational runbook. No repair or
push is implied by approving the fresh baseline. Before any production action:

1. export the 34-row migration history and current fingerprints;
2. take a database backup/PITR checkpoint;
3. run `db push --dry-run --skip-vault` with the final proposed layout;
4. enumerate every proposed `repair` transition;
5. approve each version/status change explicitly;
6. run history-only repair, re-list, and rerun SELECT-only fingerprints;
7. abort deployment if fingerprints changed during history alignment.

## Strategy comparison

| Strategy | Empty initialization | Existing history | Main drawback | Recommendation |
|---|---|---|---|---|
| Retain current historical files and align gaps | Cannot initialize: the chain lacks 16 prerequisites | Could add the two proven files and mark missing versions, but needs tombstones or unavailable SQL | Pretends a partial chain is executable | Reject for fresh installs; retain only as evidence pending layout approval |
| Squashed future baseline plus history repair | Viable after exact baseline is validated | Requires controlled repair so production does not attempt baseline | Highest operational history risk | Viable, but only with staging proof and explicit production approval |
| Separate fresh bootstrap path | Viable and leaves production history untouched | No production repair needed initially | Two paths must be governed until later convergence | **Recommended now** |

## Non-DDL bootstrap plan

- **Avatars bucket:** an idempotent bootstrap checks `storage.buckets.id='avatars'`,
  inserts only when absent, and otherwise asserts public flag, 5 MiB limit,
  JPEG/PNG/WebP MIME list, standard type, AVIF off and versioning disabled.
  Storage policies remain DDL in the baseline.
- **Cron:** after `pg_cron` is available, an idempotent bootstrap checks job name,
  schedule and command. It schedules only when absent and aborts on conflicting
  definitions. Unscheduling/replacing an existing job is never implicit.
- **Catalogue:** schema initialization inserts no LEGO catalogue rows. A separate
  Rebrickable sync validates credentials, upserts by canonical set number and
  records source/update metadata. A fixture-sized deterministic catalogue is
  used for tests.
- **Configuration/reference rows:** `membership_program_config` and other
  required singleton/reference rows are versioned in a separate idempotent seed
  file. User, exchange, notification and growth data are never seeded outside
  test fixtures.

## Test protocol

For each viable layout in a disposable Supabase environment:

1. start empty stack and assert sentinels absent;
2. apply baseline and non-DDL bootstrap;
3. capture `migration list` and catalog fingerprints;
4. execute `db reset`, recapture, and require identical fingerprints;
5. test RLS with anon, owner A, owner B, unrelated authenticated C and service
   role for collection, wishlist, growth events, exchanges and notifications;
6. test pending-request cascade and accepted-exchange deletion protection;
7. rerun bootstrap twice and require no duplicate bucket, cron or reference row;
8. compare a production-history fixture with `db push --dry-run --skip-vault`;
9. test rollback by restoring the disposable database and its migration-history
   table from the pre-operation snapshot.

## Rollback and history recovery

Fresh disposable databases are rolled back by destroying/recreating the
disposable environment from the baseline. A production history-only operation
must first export `supabase_migrations.schema_migrations`; recovery consists of
applying the inverse `migration repair --status` transitions from an approved
manifest and confirming that schema fingerprints never changed. Schema rollback
is explicitly out of scope for history alignment.

## Recommended final layout

```text
docs/database/provenance/               exact Git-proven historical evidence
docs/database/                           lineage and approved truth checkpoint
supabase/migrations/                     unchanged until separate layout approval
supabase/validation/                     SELECT-only production validation
supabase/bootstrap/fresh/                future CLI-generated baseline candidate
supabase/bootstrap/non-ddl/              bucket, cron, reference/catalogue steps
supabase/tests/                           pgTAP/RLS/bootstrap regression tests
```

The recommended immediate architecture is the separate fresh-bootstrap path.
It avoids production migration-history mutation while permitting deterministic
new environments. Convergence into the active migration directory should occur
only after disposable-stack proof and a separately approved history strategy.
