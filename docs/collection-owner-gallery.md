# Three assembled-set photos

The existing primary image is the front slot. Side/detail and rear slots use the existing camera/upload picker, 8 MB JPEG/PNG/WebP validation and 15-minute signed URLs refreshed one minute early. Photos open full size with accessible labels. My Sets can replace or remove any saved photo; removal is locked during active exchanges, and front-photo removal is disabled while a set is exchangeable and its database update is conditional on availability remaining off. Metadata removal must return exactly the expected owner/item/slot/path before Storage cleanup is attempted. Matches and canonical exchange details show authorized photos, including cancelled archives. A missing optional table keeps the primary image usable. Query failures show a fixed product message rather than provider diagnostics.

## Authorization and commits

The supplemental metadata SELECT policy inherits invoker-visible collection_items rows; writes require the actual owner of the same item. Storage SELECT verifies the actual item owner equals the object namespace, for both primary and supplemental paths. No collection visibility, Storage write grants, canonical transitions, locks, availability or readiness rules change. Anonymous gallery privileges are revoked explicitly.

Inside `collection-photos`, an authenticated collector also reads objects that already sit in their own UUID folder even when no collection or angle row points at them. An unused upload candidate and the old photo left behind after a confirmed replacement have no metadata row, so a metadata-only SELECT made them invisible; PostgreSQL `DELETE ... WHERE name ... RETURNING` and the Storage remove request both read relation columns and therefore need SELECT plus DELETE on the same row, otherwise they match zero rows. The added branch is exactly `bucket_id='collection-photos' AND (storage.foldername(name))[1] = auth.uid()::text`, evaluated beside the existing primary and supplemental actual-owner namespace bindings. It never crosses a bucket or another collector's folder, so non-owners still require visible collection metadata, and it adds no Storage write grant and changes no canonical RPC, lock, lifecycle rule or collection RLS policy.

Storage cleanup stays best effort and is never part of commit correctness. `cleanupOwnerPhoto(path)` sends `storage.from('collection-photos').remove([path])` and swallows every rejection, so an unreachable, rejected or silently filtered delete leaves an unreferenced object instead of failing a saved photo. The owner-self read branch only lets that remove see and delete the owner's own unreferenced object; it grants no other folder and authorizes no other owner’s object. Actual hosted API byte removal remains a separate verification.

Existing slots use compare-and-swap on the previous path. Empty slots use INSERT and the item/angle unique key. Only exactly one returned row matching item, owner, angle and new path authorizes old-object cleanup or success. Zero returned rows or definitive SQLSTATE rejections (including transaction rollback 40001/40P01) clean the new candidate; ambiguous network/lost-response outcomes retain it. Account generation and DOM checks prevent late hydration into another account or detached host; a same-account auth refresh safely aborts pending hydration. A session change between upload and metadata write can retain an unreferenced candidate conservatively.
